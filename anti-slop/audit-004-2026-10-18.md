## Findings

### 19. HIGH, order submission blocked. The mobile number field can never be valid

`src/pages/checkout.astro:63`

```
pattern="^(09|\\+639)\\d{9}$"
```

The doubled backslashes survive into the HTML attribute. The browser compiles
`^(09|\\+639)\\d{9}$`, which reads "09", or one-or-more literal backslashes followed by 639, then a
literal backslash and nine `d` characters. No phone number can match it.

Evidence, in page: `09171234567` **REJECTED**, `+639171234567` **REJECTED**, message "Please match the
requested format." The empty-form probe shows the browser stopping on
`["name","email","phone","street","province","city","zip"]`, and `phone` can never be cleared, so the
form is unsubmittable even with a correct address. This is the first thing a real buyer hits.

Suggested patch, one attribute:

```
pattern={'^(09|[+]639)[0-9]{9}$'}
```

The character class removes the escape sequence that the attribute doubling breaks.

### 20. HIGH, order submission blocked. The GCash and Maya reference field can never be valid

`src/pages/checkout.astro:179`

```
pattern="\\d{13}"
```

Same root cause: the rendered regex is a literal backslash followed by thirteen `d` characters.
The field becomes `required` once GCash or Maya is selected (probe: `required = true`), so that
payment path is unsubmittable too.

Evidence, in page: `1234567890123` **REJECTED**.

Suggested patch, one attribute: `pattern="[0-9]{13}"`

Both patterns are the only two doubled-backslash attributes in `src` (checked), so these two lines are
the whole of the root cause.

### 21. HIGH, layout and keyboard. The closed cart drawer stays `display: flex`

`src/components/CartDrawer.astro:153` `.cart-dialog { display: flex; ... }` overrides the user agent's
`dialog:not([open]) { display: none }`. The dialog keeps its layout box and sits translated one full
width to the right of the viewport, on every page (it lives in the layout).

Measured at a 1249px viewport: the drawer box runs from 1249 to 1697, `documentElement.scrollWidth` is
1697 against a 1249 viewport, and the page pans 448px sideways. At a 375px phone viewport,
`scrollWidth` is 750 against 375. Removing the dialog returns both to exactly the viewport width.

Keyboard consequence: the tab order after the last footer link continues into the closed drawer,
"Close cart", "Explore Drop 001", the order note, "Go to cart", "Checkout", all invisible off-screen,
and focusing them scrolls the page to `scrollX = 448`, where it stays.

Suggested patch, verified at runtime by injecting the rule (no repo edit made): make the base
`display: none` and add `display: flex` to `.cart-dialog[open]`. The existing
`transition: display .3s allow-discrete` and `@starting-style` block still animate both directions.
Probe result with the rule in place: closed drawer `display: none`, `scrollWidth` 1249, pan 0, zero tab
stops inside the closed drawer; open drawer `display: flex` with `:modal` true; Escape returns it to
`display: none`.

The size guide `<dialog>` in `AddToCartForm` is not affected: the `.cart-dialog` rule is
component-scoped, so that dialog computes `display: none` while closed.

### 22. LOW. Back from the thank-you page leaves a dead submit button

Repro: submit a valid order, land on `/order-thank-you`, press Back.

Result: back on `/checkout` with the button still reading "Logging Request Slip..." and carrying
`pointer-events-none`, so it cannot be pressed again without a reload. The cart badge is correctly
empty. Cause: `checkout.astro:440-441` sets the loading label and `pointer-events-none` optimistically
with no reset path. A `pageshow` listener that clears both would close it, or the class can be dropped
and the navigation left to do the work.

## Notes, not findings

- The empty-slip error box is reachable only when the form is valid and the cart is empty, for example
  after removing the last item from the drawer while on checkout (verified). With the default empty form
  the browser's own field validation runs first, so the box stays hidden. The box is a second line of
  defence most users will never see; disabling the submit button while the count is zero would say the
  same thing sooner.
- `README.md:44` still claims "The site publishes no prices, stock levels or delivery claims". The site
  publishes ₱325 and the delivery fee now, so that line is stale. Left alone, it is an owner document.
- Cannot be verified offline: Netlify's form handling. Locally the POST to `/order-thank-you` is answered
  by the static server and the flow lands on the thank-you page; the production submission needs a test
  on the live deploy.

## Harness notes

The first drafts failed for reasons that were the harness, not the site, and each was fixed before this
record: `innerText` uppercases `text-transform` text; headless Chrome defaults to reduced motion; a
button needs a `keyDown` carrying text to fire on Enter; native validation runs before the `submit`
event, so the empty-slip branch is unreachable from an empty form; the dialog's 300ms exit transition
keeps it in the top layer, which swallows a click sent 260ms after closing it; and `location.pathname`
carries no trailing slash on this build.
